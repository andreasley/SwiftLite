Questions:
- Where to start the async loading?
- Where to store the results?
- Where to use functions, where macros?
- 

Goals:
- Extremely easy to use for the "user" (consumer of the library), so no manual handling of loading, states, progress, errors etc.
	- Live-updates and autosaving for Models
	- Live-updates of lists of both Snapshots and Models
	- Passing of references (e.g. Snapshots) to views that then asynchronously the respective a Model
	- Ability to force-refresh lists and objects?
- Async loading
- Non-optional @State properties for existing objects
- Support "vanishing" objects (e.g. deletion)
- Unload data and cancel database change notifications when a view disappears (potentially after a delay)
- Reliable, fast code-completion

===============================================================
Load and store directly in the "Caller"
===============================================================
e.g. NavigationLink

	NavigationLink("Detail") {
		SomeDetailView()
	}

- Could preload with a `.task` on the NavigationLink and only enable the NavigationLink when preloaded. However this would preload a potentially huge number of objects if the NavigationLinks are in a List, e.g. a navigation column.
- A `.task` on the `SomeDetailView()` is possible, but wouldn't be able to send its result to that detail view, so there's no point to it.
- Not the right place to store anything related to the detail view



===============================================================
Load and store directly in the detail view
===============================================================

- A `.task` in the detail view would be called once the view appears (good)
- Async loading here would mean that the object isn't fetched when the view appears and therefore necessitate that the @State is optional and state details would have to be manually handled in the view's body (not great)

===============================================================
Load in the detail view, store everything in a nested property
===============================================================

- A `.task` in the detail view would be called once the view appears (good)
- It would be possible to have a single @State that manages all the objects-to-load in a single class and provides a `status` that can be checked in the view's body (acceptable)

===============================================================
Load and store in an intermediate view
===============================================================

- A `.task` here would be called once the view appears (good)
- The actual detail view could be nested and shown when all the objects have been fetched from the `Database`
- A suitable place to store things related to the detail view, although the actual detail view would preferably be the one to hold and manage the objects in the end. 
- There are situations where an object "vanishes" (e.g. deleted). To handle this, the intermediate view would have to be the one to manage loading/unloading (because the goal is for the detail view to use a non-optional property).
	- For this, the intermediate view would need to be the receiver of such change notifications or observe a `isDeleted` property on the object or its metadata. Since an object can be deleted while still having unsaved changes in a SwiftUI form, there should be some user interaction anyway.
- The intermediate view could be generated by a Macro and called by a static func on the user-created view
- The Macro for the intermediate view could copy the autosaving/autoupdating parameters from the user-generated view's declared properties when initializing the respective models for the properties, thereby taking care of another headache


Decisions:
- The user-created view uses non-optional properties
- An intermediate view handles states (loading, loaded, error, missing) and initiates loading/unloading. This view can be generated automatically by annotating the user-created view with a macro.
